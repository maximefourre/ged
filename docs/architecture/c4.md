# GED — C4 architecture diagrams

A visual companion to `AGENTS.md` and the design specs in
`docs/superpowers/specs/`. The prose is the source of truth; these diagrams are the
map you read first.

Four zoom levels, following the [C4 model](https://c4model.com):

| View | Question it answers |
|---|---|
| [L1 — System Context](#l1--system-context) | Who talks to GED, and what does GED talk to? |
| [L2 — Containers](#l2--containers) | What runs, as which process, storing what? |
| [L3 — Components](#l3--components) | Inside `web` and `worker`, what are the moving parts? |
| [Dynamic views](#dynamic-views) | How do the three tricky flows actually unfold? |

All diagrams are Mermaid — they render on GitHub, in most IDEs, and in Claude
Artifacts, with no build step.

## L1 — System Context

GED is an internal, non-internet-facing document store. Its primary users are **other
applications**, not humans: they authenticate with OAuth2 client_credentials JWTs and
drive everything over `/api/v1`. A single admin persona uses the web UI to provision
departments, register clients, and grant access. Two outbound directions matter and
are easy to forget: GED **calls back** into client-hosted endpoints after an async
upload (the SSRF surface), and optionally **exports** telemetry.

> **Sources:** `docs/superpowers/specs/2026-07-08-ged-design.md`, `config/routes.rb`,
> `docker-compose.yml`.

```mermaid
C4Context
    title L1 — GED system context

    Person(admin, "GED Admin", "Manages departments, app clients, permissions and the trash via the web UI")
    System_Ext(clients, "Internal applications", "Business apps that upload, list, download and tag documents over /api/v1")

    System(ged, "GED", "Self-hosted document store. Departments are folders and the permission boundary. Documents carry a key-value tag map")

    System_Ext(idp, "OAuth2 / OIDC provider", "Issues RS256 client_credentials JWTs and publishes JWKS. Today a local stand-in, later the company IdP")
    System_Ext(callbacks, "Client callback endpoints", "Client-hosted HTTP endpoints that receive async upload results")
    System_Ext(otel, "OTLP backend", "Optional. Traces and metrics. Local grafana/otel-lgtm in dev")

    Rel(admin, ged, "Administers", "HTTPS + session cookie")
    Rel(clients, ged, "Uploads / lists / downloads / tags documents", "HTTPS + Bearer JWT")
    Rel(clients, idp, "Requests an access token", "client_credentials")
    Rel(ged, idp, "Fetches signing keys", "JWKS over HTTPS")
    Rel(ged, callbacks, "Posts async upload results", "HTTPS POST")
    Rel(ged, otel, "Exports traces and metrics", "OTLP/HTTP")

    UpdateLayoutConfig($c4ShapeInRow="3", $c4BoundaryInRow="1")
```

**Read this way:** clients get a token from the IdP, then present it to GED; GED never
talks to the IdP about a specific token — it only caches the signing keys and verifies
locally. Client provisioning is *manual*: a client existing in the IdP is not enough,
an admin must also register its `client_id` in GED and grant department access.

## L2 — Containers

One deployable unit per Docker Compose service. The shape that matters most here is
the **shared `storage` volume**: `web` writes staging files that `worker` reads, and
`worker` writes Active Storage blobs that `web` serves. That coupling is why worker
scaling is same-host only.

> **Sources:** `docker-compose.yml`, `config/queue.yml`,
> `docs/superpowers/specs/2026-07-13-worker-scaling-design.md`.

```mermaid
C4Container
    title L2 — GED containers

    Person(admin, "GED Admin")
    System_Ext(clients, "Internal applications")
    System_Ext(callbacks, "Client callback endpoints")

    System_Boundary(ged, "GED — Docker Compose stack") {
        Container(web, "web", "Rails / Puma behind Thruster", "Serves /api/v1 for clients, /admin for humans and /api/docs. Thruster caps request bodies at MAX_REQUEST_BODY before Rack sees them")
        Container(worker, "worker", "Solid Queue supervisor — ./bin/jobs", "Same image as web. Two isolated pools: uploads and default. Hot-scalable on one host")
        ContainerDb(pg, "postgres", "PostgreSQL 17", "App data plus the Solid Queue schema in its own queue database")
        Container(storage, "storage volume", "Local disk", "Active Storage blobs and storage/staging. Mounted by both web and worker")
        Container(oauth, "oauth-provider", "Sinatra + SQLite", "Temporary dev IdP. Issues RS256 tokens and serves JWKS. Swapped for the company IdP by config alone")
        Container(lgtm, "otel-lgtm", "Grafana OTel stack", "Optional. Enabled only under the otel compose profile")
    }

    Rel(admin, web, "Admin UI", "HTTPS")
    Rel(clients, web, "REST API", "HTTPS + Bearer JWT")
    Rel(web, oauth, "Fetches JWKS every 300s", "HTTP")
    Rel(web, pg, "Reads and writes plus enqueues jobs", "SQL")
    Rel(worker, pg, "Claims jobs with FOR UPDATE SKIP LOCKED", "SQL")
    Rel(web, storage, "Writes staging files and serves blobs", "File I/O")
    Rel(worker, storage, "Reads staging files and writes blobs", "File I/O")
    Rel(worker, callbacks, "Delivers upload results", "HTTPS POST")
    Rel(web, lgtm, "Exports telemetry", "OTLP")
    Rel(worker, lgtm, "Exports telemetry", "OTLP")

    UpdateLayoutConfig($c4ShapeInRow="3", $c4BoundaryInRow="1")
```

**Notes worth carrying:**

- `worker` waits on `web` being healthy — only `rails server` runs `db:prepare`, so
  `web` must have migrated before a worker boots.
- `worker` scales with `bin/worktree-stack scale N`; replicas coordinate purely
  through Postgres, and recurring tasks are deduped by a unique `[task_key, run_at]`
  index, so N replicas do not mean N purge runs.
- `otel-lgtm` has deliberately **no** `depends_on` from `web`: with
  `OTEL_EXPORTER_OTLP_ENDPOINT` empty the SDK never loads, so ordering is moot.

## L3 — Components

### L3a — Inside `web`

Two entirely separate front doors sharing one Rails app: `Api::V1::BaseController`
(JWT, `ActionController::API`) and `Admin::BaseController` (Devise session). They do
**not** share controllers — the one thing they genuinely share is `DocumentCreator`,
the single path through which every document is created, including from the job.

> **Sources:** `app/controllers/`, `app/services/`, `app/models/`, `lib/telemetry.rb`.

```mermaid
C4Component
    title L3a — Components of the web container

    Container_Boundary(api, "API surface — Bearer JWT") {
        Component(apibase, "Api::V1::BaseController", "ActionController::API", "authenticate_app_client! plus the whole error contract: 401, 403, 404, 400, 422")
        Component(apidocs, "DocumentsController + DocumentTagsController", "Controllers", "index, create sync and async, show, download, destroy, replace tags")
        Component(apidept, "DepartmentsController + UploadRequestsController", "Controllers", "Lists and creates departments. Polls async upload requests")
    }

    Container_Boundary(auth, "Authentication and authorization") {
        Component(validator, "Auth::TokenValidator", "Service", "Verifies RS256 signature, issuer, expiry and the token binding — aud or required scope")
        Component(jwks, "Auth::JwksCache", "Process-local singleton", "300s TTL. Serves stale keys if refresh fails. Fails closed if it never fetched")
        Component(appclient, "AppClient + ClientDepartmentAccess", "Models", "can_access? walks Department#self_and_ancestors over grants where the mode column is true")
    }

    Container_Boundary(shared, "Shared domain services") {

        Component(adminctl, "Admin controllers", "Controllers + ERB", "Dashboard, departments, app clients, documents, upload requests, trash, queue pause")
```

**The authorization rule the diagram encodes:** `authorize_department!(dept, mode:)`
requires an explicit `:read` or `:write`. An unknown mode raises `ArgumentError` in
`granted_department_ids` rather than defaulting to `can_read` — a typo cannot silently
authorize a write through the read column. Read and write cascade independently down
the subtree, and **write does not imply read**.

### L3b — Inside `worker`

Four jobs, two pools. The absence of a `"*"` pool is the design decision here: Solid
Queue treats a queue list containing `"*"` as one global FIFO, so an uploads backlog
would starve callbacks and reconciliation. Explicit queues keep them isolated, and
`test/jobs/queue_coverage_test.rb` fails if a new `queue_as` is not listed.

> **Sources:** `app/jobs/`, `config/queue.yml`, `config/recurring.yml`.

```mermaid
C4Component
    title L3b — Components of the worker container

    Container_Boundary(uploads, "Pool: uploads — JOB_THREADS x JOB_CONCURRENCY") {
        Component(store, "StoreDocumentJob", "ActiveJob", "Atomic pending to processing claim. Builds the Document and completes the request in ONE transaction. Deletes the staging file")
    }

    Container_Boundary(defaultpool, "Pool: default — 2 threads, fixed") {
        Component(deliver, "DeliverCallbackJob", "ActiveJob", "Resolves once, pins the approved IP via http.ipaddr=, POSTs the result. 5 attempts with polynomial backoff")
        Component(reconcile, "ReconcileUploadRequestsJob", "ActiveJob — every 10 min", "Re-enqueues stuck pending requests and purges terminal ones after 30 days. Skipped while the queue is paused")
        Component(purge, "PurgeDeletedDocumentsJob", "ActiveJob — daily at 3am", "Hard-deletes past-due documents, then trashed leaf departments whose references are all clear")
    }

    ComponentDb(pgq, "Solid Queue schema", "PostgreSQL", "Job claims, recurring dedup and the pause record")
    Component(vol, "storage volume", "Local disk", "Staging files in, Active Storage blobs out")
    Component(creator2, "DocumentCreator", "Shared service", "Same code path the controllers use")

    Rel(store, creator2, "Creates the document")
    Rel(store, vol, "Reads then deletes the staging file")
    Rel(store, deliver, "Always enqueues, success or failure")
    Rel(reconcile, store, "Re-enqueues stuck requests")
    Rel(store, pgq, "Claims and updates")
    Rel(deliver, pgq, "Claims and retries")
    Rel(purge, vol, "Triggers async blob purge")

    UpdateLayoutConfig($c4ShapeInRow="3", $c4BoundaryInRow="1")
```

## Dynamic views

### D1 — Bearer auth and department authorization

Every `/api/v1` request runs this. Note that nothing here calls the IdP per request:
key material is cached for 300s, and the cache deliberately serves **stale keys** if a
refresh fails, but **fails closed** if it never managed a first fetch.

> **Sources:** `app/controllers/api/v1/base_controller.rb`, `app/services/auth/`,
> `app/models/app_client.rb`.

```mermaid
sequenceDiagram
    autonumber
    participant C as Internal application
    participant B as Api::V1::BaseController
    participant TV as Auth::TokenValidator
    participant JC as Auth::JwksCache
    participant IdP as OAuth2 provider
    participant AC as AppClient

    C->>B: POST /api/v1/documents<br/>Authorization: Bearer ...
    alt header missing or malformed
        B-->>C: 401 missing bearer token
    end
    B->>TV: call(token)
    TV->>JC: signing keys
    alt cache cold or older than 300s
        JC->>IdP: GET /.well-known/jwks.json
        alt fetch fails and keys were cached before
            IdP--xJC: error
            Note over JC: serves stale keys
        else fetch fails and cache never filled
            JC-->>TV: fail closed
            TV-->>B: InvalidToken
            B-->>C: 401 invalid token
        end
    end
    JC-->>TV: JWKS
    Note over TV: verifies RS256 signature, iss, exp<br/>and the token binding — aud or required scope
    TV-->>B: client_identifier
    B->>AC: find_by(client_identifier)
    alt not registered in GED
        B-->>C: 403 client not registered
    end
    B->>AC: can_access?(department, mode: :write)
    Note over AC: walks Department#self_and_ancestors over<br/>grants where can_write is true.<br/>Unknown mode raises, never defaults to read
    alt no grant on the department or an ancestor
        AC-->>B: false
        B-->>C: 403 forbidden
    end
    AC-->>B: true
    B-->>C: 201 Created
```

### D2 — Async upload

Triggered purely by the presence of `callback_url` on the same
`POST /api/v1/documents` endpoint. The point of this view is the **exactly-once
boundary**: document creation and request completion share one transaction, so a crash
mid-job persists nothing and the retry stores the document exactly once. Job runs and
callback deliveries remain at-least-once.

> **Sources:** `app/controllers/api/v1/documents_controller.rb`,
> `app/jobs/store_document_job.rb`, `app/jobs/deliver_callback_job.rb`,
> `docs/superpowers/specs/2026-07-15-callback-ssrf-pinning-design.md`.

```mermaid
sequenceDiagram
    autonumber
    participant C as Internal application
    participant W as web
    participant P as CallbackUrlPolicy
    participant S as StagingStore
    participant Q as Solid Queue
    participant J as StoreDocumentJob
    participant D as DeliverCallbackJob
    participant CB as Client callback endpoint

    C->>W: POST /api/v1/documents<br/>file + callback_url + tags
    W->>P: decide(url) — syntactic, no DNS
    Note over P: rejects loopback, RFC1918, link-local,<br/>CGNAT, IPv4-mapped IPv6 and numeric<br/>IPv4 encodings normalised in-process
    alt target not routable
        P-->>W: refuse
        W-->>C: 422 invalid callback_url
    end
    W->>S: write raw bytes to storage/staging/<id>
    W->>Q: enqueue StoreDocumentJob on the uploads queue
    W-->>C: 202 Accepted + request_id

    opt client prefers polling
        C->>W: GET /api/v1/upload_requests/:id
        W-->>C: same payload shape as the callback
    end

    Q->>J: claim
    Note over J: atomic pending to processing claim<br/>so a reconcile re-enqueue cannot double-store
    critical one transaction
        J->>J: DocumentCreator.call — tags, uploaded_at, stored_async
        J->>J: upload_request completed + document_id
    option job crashes
        Note over J: nothing persisted, retry stores exactly once
    end
    J->>S: delete the staging file
    J->>Q: enqueue DeliverCallbackJob on the default queue

    Q->>D: claim
    D->>P: decide(url, resolve: true)
    Note over D: resolves ONCE via Addrinfo.getaddrinfo,<br/>then pins http.ipaddr= while keeping the<br/>hostname for Host, SNI and cert —<br/>no rebinding window
    alt unresolvable or now non-routable
        D-->>D: refuse and log, no retry
    else approved
        D->>CB: POST request_id, status, document_id,<br/>error_message, tags, metadata
        Note over D: 5 attempts, polynomial backoff,<br/>logs on final failure
    end
```

### D3 — Soft delete, trash and purge

Deleting is never immediate. Documents get a 30-day timer; **departments do not** —
they are purge-gated on their references being gone, which is why there is no
`departments.purge_at` column.

> **Sources:** `app/models/document.rb`, `app/models/department.rb`,
> `app/controllers/admin/deleted_documents_controller.rb`,
> `app/jobs/purge_deleted_documents_job.rb`.

```mermaid
sequenceDiagram
    autonumber
    participant A as Client or Admin
    participant W as web
    participant DB as PostgreSQL
    participant AD as Admin Trash
    participant PJ as PurgeDeletedDocumentsJob
    participant AS as Active Storage

    rect rgb(240, 240, 245)
        Note over A,DB: Document path — timer-based
        A->>W: DELETE /api/v1/documents/:id or admin delete
        W->>DB: soft_delete! — deleted_at = now, purge_at = now + 30 days
        Note over DB: default_scope hides the row on every read path.<br/>with_deleted, deleted and purgeable are the escape hatches
        W-->>A: 204 No Content
    end

    alt admin restores within the window
        AD->>DB: Document#restore! — clears deleted_at and purge_at
        Note over AD,DB: also clears the department's soft delete<br/>if the doc came back into a trashed one
    else window elapses
        PJ->>DB: Document.purgeable.find_each(&:destroy!)
        DB->>AS: default async blob purge
    end

    rect rgb(240, 245, 240)
        Note over A,DB: Department path — reference-gated, no timer
        A->>W: delete a department
        alt it has sub-departments
            W-->>A: blocked
        else it still holds documents or upload requests
            W-->>A: confirm_deletion page — Move everything, or Trash
        end
        W->>DB: soft_delete! — leaf-only, checked UNSCOPED
        Note over DB: one transaction: hides the department and<br/>bulk-trashes its live docs with identical purge_at.<br/>API-invisible, so no new upload can land in it
    end

    PJ->>DB: for each trashed department, check UNSCOPED
    Note over PJ,DB: no Document.with_deleted under it,<br/>no upload_requests, no Department.with_deleted children
    alt all references clear
        PJ->>DB: destroy! — cascades client_department_accesses
    else something still references it
        Note over PJ: skipped this run, retried tomorrow
    end
```

## Deliberate constraints these diagrams encode

| Constraint | Why | Where it bites |
|---|---|---|
| `web` and `worker` share the `storage` volume | Staging files are written by web and read by worker; blobs are written by worker and served by web | Scaling is **same-host only**. Multi-host needs object storage first |
| No `"*"` queue pool | Solid Queue would collapse both queues into one global FIFO | An uploads backlog would starve callbacks and reconcile |
| Write does not imply read | The two grant columns are independent | A write-only client still gets the created document echoed back — that is the result of its write, not a read |
| Departments are the only permission boundary | Access covers the whole subtree, no per-subfolder rules | There is no finer-grained model to fall back on; grants never escalate upward |
| Token binding is mandatory | A shared company IdP issues tokens for every internal API under the same `iss` | At cutover, set `GED_OIDC_TOKEN_BINDING` to `audience` **or** `scope`; the app refuses to boot in production without the matching value |
| Client provisioning is manual | The real IdP's claim structure is unknown | A valid token from an unregistered client gets **403**, never auto-provisioning |

## Keeping this file honest

**This is enforced, not aspirational.** `test/integration/c4_diagrams_test.rb` fails
the suite when the model drifts from the code — exactly like `api_docs_test.rb` does
for the OpenAPI contract. It checks that every Docker Compose service, every
ActiveJob, every service object under `app/services/`, every recurring task in
`config/recurring.yml` and every Solid Queue pool in `config/queue.yml` is named
somewhere in this file. Add a job, and `bin/ci` goes red until L3b mentions it.

Deliberately *not* enforced, because the diagrams group them on purpose: the nine
`Admin::*` controllers, and the models. An over-strict test gets deleted rather than
satisfied — those stay on the honour system below.

Update these diagrams when any of the following changes — same rule as the OpenAPI
contract in `AGENTS.md`:

- a Docker Compose service, volume or scaling property → **L2**
- a new `/api/v1` endpoint, controller or service object → **L3a**
- a new job or a change to `config/queue.yml` / `config/recurring.yml` → **L3b**
- a change to the auth chain, the async upload pipeline, or the delete/purge
  semantics → the matching **dynamic view**
- the IdP cutover, when `oauth-provider` is retired → **L1** and **L2**
