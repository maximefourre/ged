# Chaos campaign — crash mid-load, zero-loss verification (2026-07-13)

Question answered empirically: **if the app (Puma + Solid Queue in-process)
is SIGKILLed mid-load, are queued documents lost?** → **No.**

## Protocol

`bin/perf-upload --profile mix --count 300 --chaos` against the worktree
Docker stack: async load, `docker kill` (SIGKILL) of the `web` container once
half the POSTs are accepted, `docker compose start web`, then convergence
polling with `ReconcileUploadRequestsJob` triggered between rounds. SIGKILL
means `StoreDocumentJob`'s `ensure` cleanup never runs — the worst case.

## Definitive run (perf-20260713-103549-106a9d)

Timeline (UTC): first POST 08:35:49 → kill ≈ 08:35:50 → web back **3 s**
after kill → backlog drained immediately → last stragglers recovered by
reconcile at **08:46:03** (= the 10-minute `STUCK_AFTER` guard, as designed).

| metric | value |
|---|---|
| request rows server-side | 168 (the other POSTs failed at connection level during the ~3 s outage — no 202, client retries, correct) |
| completed | **167 / 167 recoverable** |
| failed | 1 — killed between the DB row commit and the staging-file write: no staging file, no job, **no 202 sent**; reconcile flagged it `failed` ("staged file lost before processing") + callback, instead of leaving it dangling |
| recovered by reconcile (10-min window) | 3 requests, all `completed` at 08:46:03 |
| documents for the run | 167, **0 duplicates** |
| non-terminal requests left | 0 |

Every upload acknowledged with a 202 ended `completed` with its document
retrievable. The single `failed` row was never acknowledged to the client.

## Recovery mechanics observed

1. **Postgres-backed durability**: the `UploadRequest` row, the staging file
   (`storage/staging/<id>`, named Docker volume) and the Solid Queue job
   (dedicated Postgres queue DB) are all persisted before the 202.
2. **Restart drains the queue**: enqueued-but-unclaimed jobs resume
   immediately when the container comes back (3 s here).
3. **`ReconcileUploadRequestsJob` catches the razor edges**: jobs killed
   mid-`perform` (row stuck `processing`) and rows whose job enqueue never
   happened are re-enqueued or failed-with-message once they are 10 min
   stale (`STUCK_AFTER`) — observed live at 08:46:03.

## At-least-once caveat (earlier 1000-doc run, perf-20260713-012256)

A larger overnight run produced **1 duplicate document** out of 613: the
worker was killed *after* committing the document but *before* marking the
request `completed`; recovery legitimately re-ran the job. Crash recovery is
**at-least-once**, not exactly-once — callers that must dedup can use a tag
(e.g. an idempotency key in `tags`) or filename. Zero documents were lost in
that run either (11 732/11 732 requests eventually `completed`).

## Test-harness gotcha (documented for posterity)

Two earlier chaos runs *appeared* to fail zero-loss because the MacBook
idle-slept mid-test: the Docker VM clock freezes during sleep, so the
10-minute `STUCK_AFTER` window never elapsed from the containers' point of
view. `bin/perf-upload` now re-execs itself under `caffeinate -i` on macOS
to keep the host awake for the duration. If a long-window assertion fails
mysteriously, compare `date -u` on host vs container and check
`pmset -g log` before blaming the recovery code.
