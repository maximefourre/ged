# Perf, chaos, and monkey — Rust stack (2026-11-11)

T15 of `docs/superpowers/plans/2026-11-01-rust-migration.md`. Every figure
below is copied from the run that produced it. Comparison targets are the
dedicated-worker Rails campaigns in `docs/perf/2026-07-13-worker-scaling.md`
(same three async profiles, 1 and 3 workers) and the crash notes in
`docs/perf/2026-07-13-chaos.md`.

## Conditions

- Commands: `bin/perf-upload --profile mix|many-small|few-large --mode async`
  (6 upload threads). Chaos: `--profile mix --chaos` and
  `--chaos --chaos-target worker`. Then `bin/monkey --setup` and `bin/monkey`.
- Stack: worktree compose project `ged-rust-t15-perf`, `GED_STACK` unset so
  the active stack is Rust. Web `http://localhost:3223` (`/up` 200), OAuth
  `http://localhost:9515/token`, Postgres host port 5655. One `ged` image,
  `ged serve` on web and `ged worker` on worker (`JOB_THREADS` 3,
  `JOB_CONCURRENCY` 1, the compose defaults).
- Host, from `sysctl`: 14 cores, 36 GB RAM. Same machine class as the July
  reports. The Docker VM size was not re-measured.
- Upload cap. The July 13 campaigns predate the cap (commit `010b9c4`,
  2026-07-16, default 52428800) and accepted the few-large files of
  20_000_000–100_000_000 bytes. This stack was started with
  `GED_MAX_UPLOAD_BYTES=102000000` on web and, after the correction below,
  on every worker, so those same sizes pass the body limit. `bin/monkey`
  was run afterwards on a recreated stack at the compose default
  **52428800**, so the 55 MiB probe still meets the product cap.
- `bin/perf-upload` and `bin/monkey` provision through SQL and call
  `ged run-job` when `bin/worktree-stack active` is `rust`. The Rails
  `bin/rails runner` path is unchanged. What the HTTP campaigns count is
  unchanged.

All 41 failures have the same `error_message`:

and `bin/worktree-stack scale` does not recreate existing containers, so

the default cap rejected the files over 50 MiB. Not a store bug. The three
workers were recreated at 102000000 and the profile was run again
(`perf-20261111-112304-735571`, the row above).

## Chaos

Both kills are SIGKILL of the compose service at 3 workers, profile `mix`,
count 1000. `ged run-job ReconcileUploadRequestsJob` is what the harness
calls between poll rounds.

### Kill web (`perf-20261111-112405-53f99b`)

Log: `525 accepted -> docker kill web`, then `web back up 3s after kill`.
The harness report:

```
POSTs 1000  accepted 551  errors 449
POST latency ms  p50 26  p95 163  p99 272  max 652
wall 5.0s  ingest 6614.1 docs/min  stored 4177.3 docs/min
requests completed 551  failed 0
API document count 552
zero-loss: FAILED
error sample: EOFError: end of file reached
error sample: Errno::ECONNRESET: Connection reset by peer
```

JSON `chaos.recovery_seconds` is 3.2. `accepted_before_kill` in that JSON
is 500, the configured halfway threshold, not the 525 the log printed at
the kill.

SQL after the run, tag `perf_run = perf-20261111-112405-53f99b`:

- `upload_requests`: 552 `completed`, nothing else
- `documents`: 552 rows, 552 distinct filenames, no filename with count > 1

The 449 client errors are connections reset while web was down. They were
not counted as accepted. Of the requests the server finished, 551 were
seen as 202 by the client and all 551 completed with `failed 0`. The 552nd
document is one POST the server completed and the client recorded as
`EOFError` or `ECONNRESET` instead of a 202. Nothing is missing and nothing
was stored twice. The harness prints `zero-loss: FAILED` because
`accepted` (551) is not equal to the API count (552).

`docs/perf/2026-07-13-chaos.md` (in-process Puma, `--count 300`, run
`perf-20260713-103549-106a9d`) is the other side of that razor. There, 168
request rows existed; 167 completed; **1 failed** and was never
acknowledged: the process was killed between the row commit and the
staging-file write, so reconcile marked `staged file lost before processing`
and no 202 had been sent. Documents: 167, 0 duplicates. Every upload
acknowledged with a 202 ended `completed`. The Rust run has no such
unacknowledged failure. It has one acknowledged-on-the-server request whose
202 the client did not read. The later dedicated-worker Rails web kill
(`2026-07-13-worker-scaling.md`, run `181540-29dd6b`) is the closer
protocol: 546/546 completed, the other POSTs refused while web was down,
zero loss. Rust matches that outcome except for the one response the
client did not read.

## Monkey

Run after recreating web and worker at `GED_MAX_UPLOAD_BYTES=52428800`.
`bin/monkey --setup` provisioned the four clients and the seed documents
through SQL plus `POST /api/v1/documents`, then dropped the temporary
write grant on `monkey-dept-b`. The campaign:

```
== MONKEY PENTEST REPORT ==
  auth: 7 probes  6 defended  1 gaps  0 info
  authz: 10 probes  10 defended  0 gaps  0 info
  ssrf: 14 probes  13 defended  0 gaps  1 info
  fuzz-api: 15 probes  14 defended  0 gaps  1 info
  fuzz-admin: 1 probes  0 defended  0 gaps  1 info

PROBES 47  DEFENDED 43  GAPS 1  INFO 3
```

The one gap is `auth/aud_unverified`. The probe does not send a foreign
`aud`. On any HTTP 200 from a real token it records
`GED-SEC-01: aud unverified` (expected 200, actual 200). That is the July
label for "a valid token works", not a measurement that audience checks
are off. The July 15 campaign scored the same 1 auth gap for that probe
(`docs/security/pentest-2026-07-15.md`: 7 probes, 6 defended, 1 gap).

The three info lines:

- `ssrf/unresolvable_host`: expected 202, actual 202
- `fuzz-api/spoofed_content_type`: actual 201, content type stored verbatim
  (GED-SEC-04, info in the July run too)
- `fuzz-admin/admin_login`: actual 422, `login failed (wrong credentials or
  csrf mismatch)`. The July run recorded the same info because the stdlib
  client did not complete the Devise/CSRF handshake.

July's live gaps that this run defended: the three SSRF numeric encodings,
the oversized upload (the 55 MiB probe, now under the 52428800 cap),
malformed JSON, and the huge offset. No probe returned a 5xx.

## Verdict

Steady-load runs: zero loss, zero duplicates, no 5xx, harness `zero-loss: OK`.
Worker kill: the same, exactly once, after the 10-minute reconcile. Web
kill: zero loss and zero duplicates in SQL; the harness line is `FAILED`
only because one completed request never delivered its 202 to the client.
No Rust change came out of these runs. The script edits only let the
existing drivers provision and reconcile against the Rust image.
