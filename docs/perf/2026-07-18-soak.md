# Multi-agent API soak — bug hunt (2026-07-18)

Heavy-soak traffic campaign against a live GED stack to hunt for bugs, run with
6 adaptive "client persona" agents on top of the deterministic `perf-upload` /
`monkey` drivers, under sustained concurrent load plus crash-recovery chaos.
**Report only — no code was changed.**

## Findings (2, both low / hardening)

### F1 — Auth-failure 401 bodies echo raw `jwt`-gem exception text (low) — FIXED

> **Status: fixed** — `sec(api): return a generic 401 body instead of jwt-gem
> internals`. The auth-failure path now logs the reason server-side and renders
> a generic `{"error":"invalid token"}`; regression tests added to
> `test/security/auth_matrix_test.rb` (GED-SEC-02).


The bearer-auth failure path renders the underlying library exception message
verbatim instead of a generic "invalid token". Status is always correctly 401
(no bypass), but the body discloses internals and **reflects attacker-controlled
input**:

```
Authorization: Bearer garbage
  → 401 {"error":"Not enough or too many segments"}
Authorization: Bearer <alg:none tampered JWT>
  → 401 {"error":"Expected a different algorithm"}
Authorization: Bearer <JWT with kid="../../../etc/passwd">
  → 401 {"error":"Could not find public key for kid ../../../etc/passwd"}
```

Confirmed by hand. Impact: implementation fingerprinting + reflected `kid`; no
auth bypass in any tested case (`alg=none`, tampered signature, kid traversal,
malformed JWT all rejected). Suggested hardening: return a generic
`{"error":"invalid token"}` for all auth failures; don't echo the `kid`.
Root cause is in the token-validation rescue/render path
(`app/controllers/api/v1/base_controller.rb` `render_unauthorized` +
`Auth::TokenValidator`).

### F2 — `limit[]` / `offset[]` array params silently default instead of 400 (informational)

`GET /api/v1/documents?limit[]=1` returns **200** (falls back to the default
page size), whereas `tag[]=x`, `department_id[x]=1`, `filename[]=y` all correctly
return **400 `must be a string`**.

```
?tag[]=x            → 400   (scalar_param guard)
?department_id[x]=1 → 400   (scalar_param guard)
?limit[]=1          → 200   (int_param → 0 → default 100)
```

Root cause: `base_controller.rb` `int_param` does
`value.is_a?(String) ? value.to_i : 0`, so a non-scalar `limit`/`offset` becomes
`0` → `pagination_window` falls back to the default. This is a **deliberate
fail-safe** (the code comment states "non-positive, non-numeric or non-scalar
values fall back to the default") and carries no security or correctness impact —
it's purely an inconsistency with the strict 400 that other list params raise.
Listed for completeness; safe to leave as-is or tighten for consistency.

## What held up (the important part — nothing broke here)

- **Department permission boundary — airtight.** `no-access` sees empty lists and
  `[]` departments (no filtered leak); **write ≠ read** enforced (write-only
  client cannot read its own just-uploaded doc); **read ≠ write**; `dept-A`
  (RW dept1) fully blocked from `dept-b` on show/download/delete/tags/upload and
  `?department_id=3`. Zero cross-tenant data ever returned.
- **Soft delete.** Deleted docs → 404 on show/download/re-delete, absent from
  lists, `pagination.total` decremented. No stale visibility.
- **Concurrency / races.** Same-doc tag-replace + delete + read fired
  simultaneously → consistent final state every round (no merged/corrupt tag
  maps); 4-way concurrent `POST /departments` with an identical name → exactly
  one 201 + three 422 (no unrescued `RecordNotUnique`, no duplicate); delete
  races idempotent; pagination stayed consistent (`total ≥ len`) while a writer
  added rows. No 5xx in 38 concurrent-burst rounds.
- **Input validation.** Non-scalar params (except the F2 fail-safe), bad ISO8601,
  bad `upload_mode`, `tag_value` without `tag` → 400; pagination overflow
  (`offset` beyond int64) clamped, no `PG::NumericValueOutOfRange`; malformed
  JSON body → 400; oversized upload → rejected at the edge (413) and 422; tag
  count/key/value limits → 422.
- **SSRF callback guard.** Every private/loopback literal + numeric encoding
  (decimal `2130706433`, hex `0x7f000001`, octal `0177.0.0.1`, short `127.1`),
  IPv6 `::1`, link-local metadata `169.254.169.254`, CGNAT, IPv4-mapped IPv6, and
  userinfo-confusion URL → **422 at request time**. A `nip.io` DNS-rebinding host
  got 202 at request time then was correctly **refused at delivery** (verified in
  worker logs: `Callback refused ... must not target a private or internal
  address`).
- **Zero-loss under load & crash.** 8000+ async docs across 7 steady campaigns all
  reached `completed` with matching API counts. Web SIGKILL mid-load: all 365
  accepted requests recovered, web healthy again in 5.7 s, zero-loss OK. Worker
  SIGKILL mid-load: all 500 requests reconciled to `completed` (api count 500/500),
  zero-loss OK — after the ~10-min window described below.

## Operational note (behavior, not a bug)

Killing a **worker** mid-flight (SIGKILL) leaves its in-flight upload_requests
non-terminal — one `pending` (enqueued job lost) and one `processing` (claimed
then killed) were observed — until `ReconcileUploadRequestsJob` re-enqueues them.
That job's `STUCK_AFTER` is **600 s**, so worker-crash recovery has a ~10-minute
latency floor by design (at-least-once for job runs, exactly-once for documents —
see `docs/superpowers/specs/2026-07-13-perf-upload-design.md` and
`docs/perf/2026-07-13-chaos.md`). Correct, but worth an ops alert if a worker
crash leaves requests non-terminal past that window.
